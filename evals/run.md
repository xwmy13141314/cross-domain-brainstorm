# A/B 评测协议 v0.2

用于比较 `cross-domain-brainstorm` v0.1 与 v0.2，或比较不同模型/提示。

目标不是证明“新版本更好”，而是回答：

> 在同样的问题和时间预算下，v0.2 是否产出更深、更可追溯、更可测试、更安全的创意？

## 一、准备

- 版本：v0.1（基线）与 v0.2（候选）。
- Case：`evals/cases.md` 的 6 个；先跑 3 个，有信号再扩到 6 个。
- 评委：3 人（产品/设计/工程各一），至少 1 人不懂这个 skill 的内部结构。
- 工具：计时器、盲标（A/B 随机）、评分表（`evals/rubric.md`）、录音/截图。
- 模型：同一个模型、同一个温度/参数；如果模型支持系统提示，保持系统提示一致。
- 会话：每个 case × 版本用独立会话；不要让模型看到另一个版本的输出。

## 二、盲标与顺序

1. 把 v0.1 和 v0.2 随机标为 A/B（每个 case 可以不同）。
2. 随机决定先跑 A 还是 B。
3. 评委不知道哪个是 v0.2；只知道 A/B。
4. 每个评委独立打分，不讨论；合议时再看版本。

## 三、运行步骤

### 1. 安装/加载 skill

- v0.1：使用仓库 v0.1.0 的 `SKILL.md` + references。
- v0.2：使用当前仓库。
- 确保模型能读到 `SKILL.md` 和按需读取 references。
- 不要在 prompt 里额外提示“用机制卡/用红队”；让 skill 自己驱动。

### 2. 同一个 prompt

对每个 case，使用同一句用户请求。例如：

> “我们做 AI 笔记 App，用户记完不回看。帮我做一次跨域脑暴，给我几个值得推进的方向。”

不要给 v0.2 额外信息；不要给 v0.1 少信息。

### 3. 时间预算

- 主比较：Quick 模式，**15 分钟上限**；记录自然完成时间。
- 如果 15 分钟未完成，截断并标记“超时”；超时本身是负面信号。
- Deep 模式单独比较，不混入 Quick 结果。

### 4. 记录输出

- 保存完整输出（Markdown/截图）。
- 记录：开始/结束时间、是否超时、是否读取 references、是否追问、是否卡住。
- 不要编辑输出；评委看原始版本。

### 5. 评分

- 每个评委先独立填 `rubric.md`。
- 先过 10 个门槛；任何 Fail 标记“不合格”。
- 再打 7 维分。
- 合议：只讨论分歧 ≥1 分的维度；记录原因。
- 最后揭盲 A/B。

## 四、样本量与轮次

| 阶段 | Case 数 | 目的 |
|---|---|---|
| Pilot | 3 | 校准 rubric、发现明显问题 |
| Main | 6 | 主比较 |
| Deep dive | 1-2 | 对失败/争议 case 做质性复盘 |

每个 case × 版本至少 1 次；如果模型输出波动大，重复 2 次，取平均或记录方差。

## 五、判定规则

### v0.2 胜出

- 至少 4/7 维平均分高于 v0.1；
- 机制深度、可追溯、可测试、伦理中至少 3 项更高；
- 有用性/可读性不下降；
- 门槛通过率不低于 v0.1；
- 完成时间不超过 v0.1 的 1.5 倍（Quick）。

### 平手/不划算

- 只高 1-2 维，但时间明显更长；
- 机制更深但用户读不懂/不愿用；
- 伦理更好但把所有创意都 kill 了，没有可执行组合。

### v0.2 失败

- 机制深度/可追溯没有提升；
- 门槛通过率更低；
- 输出更长但更空；
- 评委更愿意用 v0.1。

失败时，不要直接改 rubric；先看是哪个环节失败（距离/机制/嫁接/收敛/红队），再改 skill。

## 六、质性复盘

每个 case 记录：

- 最好的一个创意，为什么好？
- 最差的一个创意，为什么差？
- 有没有“表面迁移”漏过测试？
- 有没有“机制卡写不出失效前提”？
- 有没有“评分偏向保守”？
- 有没有“伦理风险被忽略”？
- 用户是否知道下一步做什么？

## 八、偏差控制

| 偏差 | 控制 |
|---|---|
| 版本泄漏 | 盲标；评委不看文件名/开头 |
| 顺序效应 | 随机先 A/B；每个 case 重新随机 |
| 评委漂移 | 先校准一个样例；中途不换锚点 |
| 时长不公 | 同样 15 分钟上限；记录自然时间 |
| 提示泄漏 | 同一句 prompt；不额外提示 v0.2 的方法 |
| 选择偏差 | 6 个 case 覆盖数字/物理/高风险/公共服务 |
| 光环效应 | 先过门槛，再打分；不先看总分 |
| 沉没成本 | 预先写判定规则；不因为“做了很久”而放行 |

## 九、给评委的说明

> 你看到的是一份跨域脑暴输出。请先检查它是否说清了“借了什么机制、怎么映射、谁来验证”，再打分。  
> 不要因为“看起来专业/很长”给高分；不要因为“想法奇怪”给低分。  
> 先过门槛，再看七维。  
> 如果你不确定，写备注，不要猜。
